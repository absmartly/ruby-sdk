## [1.4.0] - 2026-11-17

A non-breaking release of 1.3.0. Code written against 1.3.0 keeps compiling and running: the 1.3.0 classes, method signatures, error types and messages, `close`/`refresh` return values, unit hashing and core extensions are unchanged. Behaviour moves only where the cross-SDK contract or a bug fix requires it; each such entry under Changed says who is affected.

### Added
- Assignment rules. An experiment's `assignmentRules` (a JSON string of `{"rules": [...]}`) are evaluated in order, and the first matching rule decides the variant, taking precedence over the audience and `audienceStrict`, traffic eligibility, full-on and custom assignments; only `set_override` beats a rule. An `assign` rule gives a fixed variant; a `split` rule (e.g. `"percentages": "20/30/50"`) hashes the unit with the experiment's own seed over its percentages, which must be non-negative and sum to 100 within 0.01. Rules can be scoped to `environments` (an empty list matches all) and their `conditions` are JSON expressions over the same attributes as audiences, including `application` and `environment`. Rule-assigned exposures carry `ruleOverride: true`, `assigned: false`, `eligible: true`, so the backend excludes them from analysis. A malformed rule is skipped in favour of the next one; an `assign` variant out of range or a split without one percentage per variant stops evaluation and falls back to normal assignment. While the unit is missing, a split rule gives the experiment's no-unit variant (the full-on variant, otherwise 0); once the unit is set, unexposed ones are re-resolved and exposed ones keep their variant. Invalid `assignmentRules` JSON is ignored for that experiment. A custom audience matcher that only implements `evaluate(audience, attributes)` keeps working: it receives the attributes under the keys they were set with, as in 1.3.0 (plus `"application"`/`"environment"`, see Changed), and rules then run on the default rule engine.
- `semver_eq`, `semver_gt`, `semver_gte`, `semver_lt` and `semver_lte` operators for audience filters and rule conditions. A leading `v`/`V` and `+build` metadata are ignored, missing core parts count as `0`, and a release ranks above its pre-releases; an operand that is not a version gives `null`. A numeric operand is converted to text as the JavaScript SDK does (`toFixed(15)`, trailing zeros trimmed), so `1.0000000000000002` compares equal to `"1"`; other operators are unchanged.
- `Context#finalize`, the name the other ABsmartly SDKs use. Unlike `close`, if the final publish fails it raises the failure (a `StandardError`) and leaves the context open with its events queued, so it can be retried; it logs the `"finalize"` event (`EVENT_TYPE::FINALIZE`) once sealed, and `experiments`, `set_override` and `set_overrides` keep working after it. `close` behaves as in 1.3.0.
- `Context#finalized?`, `#finalizing?`, `#ready_error`, `#get_unit`, `#get_units`, `#get_attribute`, `#get_attributes`, `#custom_field_value_type` and `#wait_until_ready(timeout = nil)`.
- `ABSmartly#create_context_async` and `Absmartly.create_context_async`, which return a context at once and fetch its data on a background thread.
- `Context#variable_keys_list`, mapping each variable key to every experiment that defines it, in experiment id order.
- `ABSmartly.new(endpoint, api_key:, application:, environment:, timeout:, retries:, context_event_logger:)` alongside `ABSmartly.new(config)`.
- `retry_statuses` (on `ClientConfig` and `DefaultHttpClientConfig`) to opt in to retrying HTTP statuses, e.g. `[502, 503, 504]`, and `retry_connection_failures` to opt in to retrying a refused connection on the context fetch (GET only). Both are off by default, so retries are as in 1.3.0.
- `Absmartly::ContextPublisher` and `Absmartly::DefaultContextPublisher`, aliases of `ContextEventHandler` and `DefaultContextEventHandler` under the names the other SDKs use.
- `Client#application` and `Client#environment` readers, `Absmartly::ContextDataResult`, `Absmartly::PublishError` (a `StandardError`), `Context.create`'s optional `application:`/`environment:` keywords, `Exposure#rule_override`, `Experiment#assignment_rules`, and an optional `properties` argument to `track`.

### Changed
- The `X-Agent` header is now `absmartly-ruby-sdk/<version>` instead of `absmartly-ruby-sdk`, as the JavaScript SDK sends its versioned agent. The collector stores it in the export `agent` column, so dashboards, collectors and proxies that match the exact old value need updating.
- Every exposure in the publish payload now carries `ruleOverride` (`false` unless an assignment rule chose the variant), as the JavaScript SDK sends it. Consumers that compare the exact publish body (snapshots, proxies) see the extra field.
- Audience filters and rule conditions now always see `application` and `environment` (the names configured on the client), matching the JavaScript SDK. A user attribute of the same name wins, even when set after the context is created. Empty or unset names are left out rather than matching `""`. Nothing new is published (the collector attaches both server-side) and `app_version` is never injected. Who moves: units in an experiment whose audience has an `application`/`environment` condition. With Audience enforced (`audienceStrict`) they got control (variant 0) because 1.3.0 never supplied those attributes; a matching unit is now randomised normally and gets a new exposure. Non-strict audiences stop flagging `audienceMismatch` for matching units.
- `variable_value` and `peek_variable_value` return the caller's default when the unit is not assigned to the experiment, as the JavaScript SDK does (cross-SDK scenario 48): its unit type is not set on the context, or it fails an enforced (`audienceStrict`) audience, and no override or assignment rule applies. 1.3.0 returned variant 0's (control's) value in both cases. Units outside the traffic split or in a full-on experiment read their variant's value as before, and the exposure is still queued. Who moves: code that reads variables for such units and relied on getting control's config instead of its own default.
- Shared variable keys: when several experiments define the same variable, `variable_value` and `peek_variable_value` read from the first experiment, in experiment id order, that the unit is assigned to or overridden in, exposing each experiment visited on the way (as the JavaScript SDK does). 1.3.0 always read and exposed the last experiment in the payload. `variable_keys` keeps its shape (key to one experiment name) but now names the experiment with the lowest id. Who moves: units in more than one experiment that share a variable key.
- `track` raises `ArgumentError` ("Goal '<name>' properties must be of type object.") for properties that are neither a Hash nor respond to `to_h` (e.g. a String or Array). 1.3.0 queued them, and the collector, which reads goal properties as an object, rejected the whole publish, losing every exposure and goal in it. `ActionController::Parameters` (through `to_unsafe_h`, so unpermitted params are accepted as in 1.3.0) and other `to_h` objects are converted. Who moves: code passing non-object properties to `track`.
- `set_unit` with a unit type given as a String now raises "Unit '...' already set." when the type already has a different UID, as the README always said and as it did for a Symbol type; 1.3.0 silently replaced the UID, so later exposures and goals were published under a different unit than the earlier ones. Who moves: code that calls `set_unit("type", uid)` twice with different UIDs on one context (create a new context for the new identity instead).
- `create_context` and `refresh` no longer raise connection errors such as `Faraday::ConnectionFailed` out of the fetch, as an HTTP error response already didn't in 1.3.0. `create_context` returns the context failed (`failed?` is true, reads return control and the caller's defaults); `refresh` keeps the current data. Either way the error goes to the event logger. Who moves: code that wraps `create_context` or `refresh` in `rescue Faraday::ConnectionFailed` (check `context.failed?` or the logged `"error"` event instead).
- The `"publish"` event is logged once a publish is delivered, as its documentation says ("`publish()` method succeeds"); a failed publish logs an `"error"` event instead. 1.3.0 logged `"publish"` before sending and logged nothing when the collector rejected the batch. Who moves: event loggers that counted `"publish"` events for failed publishes.
- `close` and `finalize` bound callback-driven publishing to two passes. If events are still queued after the second successful pass, they remain queued and the context stays open; a catchable retry error is raised instead of silently discarding accepted events or looping forever. A close or finalize requested by a callback in the meantime also stays pending and is carried out by the next successful publish. A `close` or `finalize` requested from inside a publish callback in that state, or from the `"error"` callback of a rejected publish, keeps the events queued and is carried out on the next successful `publish` (if that deferred seal's own publish is rejected, a deferred `finalize` stays pending and raises the rejection out of that `publish`, while a deferred `close` logs it and seals, as `close` does; if the publisher raises, either stays pending and the error is re-raised), without making the current `publish` raise (the `"error"` event for a rejected publish is new in 1.4.0, see the `"publish"` entry above). Who moves: applications that enqueue events from publish callbacks or concurrently while sealing; retry the sealing method after producers stop.
- A failed `publish` keeps its events queued and sends them with the next publish (1.3.0 dropped them), so `pending_count` stays above zero until a publish succeeds. A publisher that raises during `close` leaves the context open with the events queued instead of losing them. Who moves: code that reads `pending_count` after a failed publish, and collectors, which now receive the retried batch.
- A `refresh` that was already in flight when the initial async fetch failed, and then succeeds, recovers the context: it installs the data and clears `failed?` and `ready_error`, and events still queued are published with the next `publish` (exposures made while failed are unassigned, `assigned: false` with experiment id 0, and control unless an override forces a variant; assignments read while failed, overrides included, are resolved again when the recovered data has the experiment, so later reads and exposures carry it; such an assignment already exposed while failed is therefore exposed once more after recovery, with the real experiment id, while one for an experiment the recovered data still lacks is kept and not exposed again); a `publish` made while the context was failed still drops its events, as in 1.3.0. A `refresh` called after the context failed is still a no-op, as in 1.3.0. Who moves: code that relied on a failed async context staying failed after an in-flight refresh completed.
- A failed `refresh` logs the error and keeps the current data (1.3.0 marked the context failed and served control for every experiment from then on); it still returns what the event logger returned. Who moves: units of a long-lived context after a refresh fails, which keep their variants instead of dropping to control.
- Numeric audience comparisons compare numbers, following the JavaScript SDK's number coercion; 1.3.0 compared their text, so `10 > 9` was false. Who moves: units whose numeric attributes the text comparison misjudged; with a strict audience they move between control and their variant.
- An invalid regex in a `match` audience counts as an audience mismatch (strict audiences give control), as in the JavaScript SDK; 1.3.0 ignored the whole audience. Who moves: units in experiments whose audience has an invalid `match` pattern.

### Fixed
- A context fetch whose body can't be deserialized fails the context instead of leaving it never ready.
- `ContextDataResult`, `PublishError`, `ContextPublisher`, `DefaultContextPublisher` and the semver comparator and operators live under the `Absmartly` namespace, so none of them can clash with an application's own classes.
- Nested `variants`, `applications` and `customFieldValues` in the context payload are read by key: an unknown key no longer fails the whole context and a reordered object no longer swaps fields. Unknown experiment fields are ignored without writing to stderr. A custom field with a missing or `null` `type` is read as text instead of raising `NoMethodError` out of `create_context`/`refresh`.
- `in` with an object haystack finds symbol keys (audience attributes are parsed with symbolized names).
- An indeterminate audience result (no filter) keeps a cached assignment instead of re-assigning.
- `set_unit` accepts the same UID again when it differs only by surrounding spaces, or comes as a String instead of a number (`123` then `"123"`); 1.3.0 raised "Unit '...' already set." for a Symbol unit type in the first case. Integer and Float UIDs keep their value (`get_unit` returns the number) and hash exactly as in 1.3.0; `set_unit` still returns the UID's text.
- `Client#context_data` returns a new immutable `Absmartly::ContextDataResult` per call (with the same `success?`, `data_future`, `exception` and `promise` readers), so concurrent `create_context_async` calls and refreshes sharing a client can't read each other's in-flight state. The client's own readers still reflect the latest fetch.
- `ContextEventLoggerCallback` no longer calls ActiveSupport's `present?`, so it works outside Rails.
- A raising event logger no longer breaks the operation that logs (initialization, treatment, publish).
- `ABSmartly.new(config)` accepts a duck-typed config that responds to `to_hash` on Ruby 2.7.
- An exposure or goal can no longer be queued after `close` sealed the context.
- Clearing the override of an experiment the context data doesn't have returns control again; 1.3.0 kept returning the cleared forced variant. Who moves: units whose override of such an experiment is cleared get control instead of the stale forced variant, with one more control exposure.
